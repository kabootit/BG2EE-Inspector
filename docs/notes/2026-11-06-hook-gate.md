## Plan summary

The probe from `initial/04-reverse-engineering` interposes `glClear` and only reports. This run loaded it
into the game for the first time, to answer the question ADR-0005 left open: does the game call
`glClear` once a frame on its main thread, after its Lua starts, with Lua idle at some of those calls?
Nothing in `native/` changed for the run.

## Gotchas worth remembering

- **The game draws at most 30 frames a second by default.** `Baldur.lua` holds
  `SetPrivateProfileString('Program Options','Maximum Frame Rate','30')`. The probe counted 3600 calls
  every 123 to 124 seconds, 29.2 a second, so a count line comes about every two minutes, not every
  minute as the manual test first said. The rate is consistent with one `glClear` per frame at the cap;
  the probe does not see frames directly, so "one per frame" rests on that match.
- **Lua starts before the first frame.** The engine logs `LUA:` lines about 0.1 seconds before the first
  `glClear`, and the probe found the `lua_State*` global already set at call 1. The probe's wait for the
  global to become non-null never had to wait.
- **A failed read counts as idle in the probe.** `lua_running` returns false when
  `mach_vm_read_overwrite` fails, so "Lua running during 0" also covers reads that failed. Here that is
  unlikely: the pointer is the one the engine's own registration code loads, and a wrong `ci` offset
  would make nearly every call count as running, not none. Registration must not inherit the
  shortcut: a failed read has to mean "not safe", and get reported.
- **Steam was not running.** The log has `SteamAPI_Init() failed` and no Steam id line, unlike the three
  November 1 sessions. The game played without the client, so the Steam id redaction was not exercised
  in this session.

## Verification

Run on 2026-11-06, by the tester, against `09dc2f8` with a clean tree:

- `deno task build`, then `deno task play`. The session log, `logs/session-20261106-170943.log`, holds
  377 lines over about 18 minutes (17:09:43 to 17:27:47). The main menu lasted about 3.7 minutes
  before the save loaded (the engine's `Initializing Quests` lines at 225 seconds).
- **The `A7X` lines**, judged against the manual test's Pass criteria:

  | Condition | Line | Result |
  | --- | --- | --- |
  | 1. Known build | `A7X build 2.7.3 arm64 matched` | Present, right after the load marker |
  | 2. Main thread | `A7X probe: first glClear at 0.4s, main thread yes` | Present; no `off the main thread` line |
  | 3. Lua starts | `A7X probe: lua_State set at 0.4s, by glClear call 1` | Present |
  | 4. Every frame | Eight count lines, 3600 to 28800 calls, at 123, 247, 370, 493, 617, 740, 863 and 986 seconds | Even gaps of 123 to 124 seconds, 29.2 calls a second against a 30 frames-per-second cap |
  | 5. Idle Lua | `Lua running during 0` on every count line | 0 of 28,800 calls found Lua running |

- **The two side questions** (steps 2 and 5): the first 123 seconds were all main menu, and every gap
  between count lines stayed within a second of the others through the load, the pause and the area
  change. So the main menu and a paused game both draw frames at the full rate.
- **The rest of the log:** no `LUA ERROR`, no crash report. Its 9 `ERROR` lines are the baseline ones
  the Phase 0 note recorded (`dialogf.tlk` and four music files), present without the library too.
  No home path; `$HOME` appears in its place.
- **Not captured:** `play`'s own summary and exit code go to the terminal, not to the session log, so
  they are not part of this record. The tester confirmed the game was quit from its own menu.
