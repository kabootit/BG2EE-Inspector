> [spawn harness plan](2026-11-13-spawn-harness.md), which completed Phase 3; the project's own

## Context

Phase 3 proved the walker: party values equal the record screen, the creature list finds the
creatures in the area on screen, and spawned creatures equal their `.cre` files. Phase 4 makes that
usable: a public, versioned API other mods can build on, text in the message window, and JSON lines
for tools outside the game. The foundation plan's Phase 4 is split (decided 2026-11-13):

- **This plan: the data API and console output.** The `A7X` table, schema-1 records, the JSON
  encoder and `A7XDATA` lines, the data-model spec with a TypeScript guard and a contract check, the
  text formatter, and console commands. Loaded from `override/` by hand, as the checks are now.
- **Next: the hotkey and the install.** The WeiDU component that patches `ui.menu`, the `e` key over
  a creature (the area's hovered-object field, still to be found), portraits, and `A7X.hovered()` and
  `A7X.portrait()`.
- **Then: the example consumer mod** that proves the contract from outside.

Branch `initial/08-output`, from `main`.

## Design

### Files (`mod/inspector/lib/`, names of 8 characters at most)

| File | Global while loading | Role |
| --- | --- | --- |
| `a7x.lua` | none | the entry point: `Infinity_DoFile("a7x")` loads the rest, in order |
| `a7xoff.lua`, `a7xwalk.lua` | `A7XOFF`, `A7XWALK` | as now; the walker gains `A7XWALK.use(provider)` to take its native table from the API |
| `a7xjson.lua` | `A7XJSON` | encode-only JSON: sorted keys, integers as integers, RFC 8259 escapes, `nil` left out, an empty table as `[]` |
| `a7xfmt.lua` | `A7XFMT` | a record as message-window lines |
| `a7xapi.lua` | `A7X` | the public API |

`a7xapi.lua` keeps the other modules as locals and sets their globals to `nil`, so `A7X` is the only
global the inspector leaves. **The native table is captured lazily**: on the first API call that finds
`A7X_native`, the API keeps it as a local and sets the global to `nil`. Lazily, because once the next
slice loads the API from `ui.menu`, it may run before the library registers `A7X_native` (0.5 s into
the main menu). From then on no other Lua can make raw reads (ADR-0002).

The check scripts (`a7xchk`, `a7xlist`, `a7xspawn`) need `A7X_native` and keep working in a session
where `a7x` has not been loaded; the manual tests' README says so.

### The public API (`A7X`, API 1.0)

| Function | Returns |
| --- | --- |
| `A7X.version()` | `{ api = "1.0", schema = 1, build = "2.7.3 arm64" }` (the build from `A7X_native.Version()`) |
| `A7X.status()` | `"ok"`, `"no_native"` (no library, or a build it refused, which registers nothing either), or `"loading"` (no game loaded, or no area on screen) |
| `A7X.get(id)` | a fresh schema-1 record, or `nil` and the status or reason |
| `A7X.list(filter)` | `{ area = "<resref>", creatures = { { id, name, allegiance = { ea, side } } ... } }` for the area on screen, the same `allegiance` as a record's; filter `"enemies"`, `"party"` or `"all"` (the default) |
| `A7X.show(what)` | console output: `what` is an id, `"enemies"`, `"party"` or `"all"`; prints each record's lines with `Infinity_DisplayString` and logs each as `A7XDATA\t<json>`; with no argument, a usage line |

Every call returns fresh tables and never raises (each is wrapped in `pcall`). `A7X.hovered()` and
`A7X.portrait()` arrive with the next slice as API 1.1 (adding functions is a minor version). The
foundation plan's `"unknown_build"` status is folded into `"no_native"`: on an unknown build the
library registers nothing, so Lua cannot tell the two apart; the library's log line says which.

### Schema 1 (`docs/data-model.md`)

Only fields a check has proven. The table gives each field's type, what it means, and the check that
proved it; where each value sits in engine memory (offsets, the engine's stat numbers) is in
`docs/re-notes.md`, not in the spec, because consumers of the API never need it. Stats are the ones in
effect now, items and spells included, as the engine uses them:

| Field | Type | Meaning | Proven by |
| --- | --- | --- | --- |
| `schema` | 1 | the record format's version | |
| `id` | integer | the engine's id for the creature, valid for this game session | party check |
| `resref` | string | the name of the `.cre` file the creature was made from, up to 8 characters | spawn check |
| `name` | string | the name the game shows for it | party check |
| `allegiance` | `{ ea, side }` | whose side the creature is on: `ea`, the engine's value 0 to 255 (IESDP's `EA.IDS`: 2 a party member, 128 neutral, 255 enemy), and `side`, the same in words: `"party"` for a party member, else `"ally"` for 30 or less, `"enemy"` for 200 or more, `"neutral"` between | party check, spawn check (`ea`); creature list (`side`) |
| `hp` | `{ cur, max }` | hit points now, and the maximum | party check, spawn check (max) |
| `ac` | integer | armor class | party check, spawn check |
| `ac_mods` | `{ crushing, missile, piercing, slashing }` | AC adjustments against each kind of attack | party check, spawn check |
| `thac0` | integer | THAC0, before the bonuses of the weapon in hand (the record screen shows it after them) | spawn check |
| `saves` | `{ death, wand, poly, breath, spell }` | saving throws | party check, spawn check |
| `resist` | `{ fire, cold, electricity, acid, magic_fire, magic_cold, slashing, crushing, piercing, missile }` | resistances, in percent | spawn check |
| `mr` | integer | magic resistance, in percent | spawn check |

Not in schema 1: game time, the pause state and spells (Phase 5 adds them as optional fields, which
keeps `schema = 1`). Renaming, removing or changing a field's meaning bumps `schema`.

### Formatter (`a7xfmt.lua`)

```text
[A7X] Fire Giant  HP 112/140  AC -1  THAC0 4  MR 0%
      Saves D3 W5 P4 B4 S6  Resist fire 100
```

The name is colored by `allegiance.side` with the engine's markup, `^0x` and eight hex digits, the text, then `^-`
(from the binary's `^%#010x%s^-`, BG2EE-GameLog's finding); the byte order of the color is confirmed
by eye in the manual test. Resistances list only the non-zero ones, or `none`; AC modifiers are shown
only when non-zero.

### Deno side: one Zod schema (decided 2026-11-14)

The API runs in the game's Lua, so it stays hand-written Lua, held to the schema by tests (Lua
libraries were considered: dkjson encodes but orders keys only from a hand-written list; tableshape
checks shapes but would be a second definition of the record and needs adapting to
`Infinity_DoFile`). Outside the game, one definition serves everything:

- `src/model/schema.ts`: the schema-1 record as one Zod schema (`jsr:@zod/zod@4`, zero dependencies,
  built and signed on GitHub Actions), strict, so an unknown field fails. The TypeScript types come
  from it (`z.infer`); `parseRecord(json: unknown)` returns the record or the list of problems.
- `docs/data-model.schema.json`: the same schema as JSON Schema, generated by Zod
  (`z.toJSONSchema`) for tools outside the game that do not use TypeScript. Committed; a test fails
  when it no longer matches the Zod schema, and another when `docs/data-model.md` lists a different
  set of fields.
- `src/verify/data.ts`: `parseData(log)` finds `A7XDATA` lines; `deno task verify` judges them when
  present: every line parses through the schema. It prints each record's `allegiance.side`, name and
  HP.
- **One golden file in both languages**: `test/fixtures/a7xdata.txt` holds the `A7XDATA` lines the
  API produces for the fake game. The Lua test checks the API produces exactly those lines; the Deno
  test checks each passes the Zod schema. The Lua and TypeScript sides cannot drift apart unnoticed.
- **The dependency**: `lint:security`'s import rule and `docs/rules/toolchain.md` allow
  `jsr:@zod/zod@4` by name, beside `jsr:@std/*`; Deno downloads it into its cache from `jsr.io` on the
  first task run after the import is added, and `deno.lock` pins its integrity hash.
  `docs/requirements.md` says so.

### Tests

- `test/lua/a7xjson_test.lua`: key order, integers and fractions, escapes (quotes, backslash, control
  characters), nested tables, arrays, empty tables, refused values (functions, NaN).
- `test/lua/a7xapi_test.lua` on the fake game: the native table captured and the global cleared;
  `status` in each state; `get` for a party member, a hostile creature, a stale id; `list` with each
  filter; `show` lines and `A7XDATA` lines against the golden file; fresh tables (mutating a returned
  record does not change the next); no raise when the walker fails.
- `test/lua/a7xfmt_test.lua`: the lines for the fake game's creatures, colors by side.
- `test/model/schema_test.ts`, `test/verify/data_test.ts`: the schema on the golden lines and on
  broken ones (an unknown field, a missing one, a string for a number, schema 2); the JSON Schema file
  and `data-model.md`'s field list in step with the Zod schema.
- `test/lint/security_test.ts`: `jsr:@zod/zod@4` allowed, an unpinned or other `jsr:` package still
  refused.

### Docs

- **ADR-0006** (new): plain Lua tables in the game, JSON lines at the boundary, one versioned model
  (the Zod schema, the prose spec, the Lua producer), `A7X` as the only public global, the native
  table captured and cleared; options considered: hand-written guard, TypeSpec (an npm compiler, no
  Lua output), Lua libraries; Hono and Drizzle are for a later viewer or storage.
- **ADR-0003** fold-in: Zod as the second allowed import source, and why.
- **ADR-0002**: status active (the Phase 3 gate passed); fold-in: the file names, `unknown_build`
  folded into `no_native`, the API's schedule (1.0 now, 1.1 with the hotkey slice).
- `docs/api.md` (new): the public contract: functions, statuses, versioning, load order, fresh
  tables, the `A7XDATA` lines for tools outside the game.
- `docs/data-model.md` (new): the schema-1 table above, with units and validation status, linking
  `docs/data-model.schema.json`.
- `docs/manual-tests/api.md` (new, "Data API") and its index row, about 15 minutes:
  1. copy the six files into `override/`; build, `play`, load a save in an area with creatures, some
     hostile if possible;
  2. console: `Infinity_DoFile("a7x")`, then `A7X.show("party")`, `A7X.show("enemies")`,
     `A7X.show("all")`, and `A7X.show(<an id from the output>)`;
  3. console: `Infinity_DisplayString(tostring(A7X_native))`, which must print `nil`;
  4. compare one party member's HP, AC and saves with the record screen; note how the colors look;
  5. quit, remove the files, `deno task verify`.

  Pass when `verify` parses every `A7XDATA` line through the schema, the party records match the record
  screen (THAC0 aside, which the record screen adjusts for the weapon), `A7X_native` reads `nil`, and
  nothing raised a Lua error.
- `docs/manual-tests/README.md` (the check scripts need a session without `a7x` loaded), `TODO.md`,
  foundation plan note, `CLAUDE.md` (layout, `src/model/`, `deno task schema`), `docs/README.md`,
  `docs/rules/docs.md` (the reference docs' source files by their new names).
